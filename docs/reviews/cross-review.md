## 1. Мета та критерії

Відповідно до **завдання 6** методичних вказівок необхідно:

Завдання **1–5** розподілені між учасниками; завдання **6** виконується спільно. Додаткова перевірка DRY, KISS і YAGNI корисна, але у наданому тексті завдання 6 **не є окремим обов'язковим пунктом**.

**Обсяг рецензування:**
- Дем'ян перевіряє реалізацію Едуарда в пакеті `variant1_orderprocessing` (16 Java-файлів).

- Обидва переглядають відмінності між реалізаціями, фінальний стан Git та вміст метрик.

**Суттєве архітектурне застереження:** станом на момент перевірки в одній гілці співіснують **дві окремі Java-програми** (`ua.edu.lab8.Main` і `variant1_orderprocessing.Main`). Вони компілюються як різні пакети; робота однієї програми не доводить, що в ній задіяні всі патерни іншої. Методичка прямо допускає окремі реалізації за різних мовних стеків; щодо двох окремих реалізацій на **одній** мові умова інтеграції не сформульована однозначно. Це слід уточнити в викладача, а не представляти інтеграцію як уже виконану.

## 4. Аналіз якості командного рішення

### 4.1. DRY (додаткова перевірка)
- **Проблема:** дві версії `Customer`, `Order`, `Product`, `OrderItem`, дві програми `Main` — дублювання предметної області. Це може бути прийнятним для окремих навчальних етапів / незалежних варіантів реалізації, але не для єдиного фінального продукту без пояснення.
- **Що вирішити:** уточнити у викладача, чи має фінальний результат бути єдиним застосунком. До відповіді **не видаляти** файли або рефакторингову історію.

### 4.2. KISS (додаткова перевірка)
- **Позитивне:** короткі інтерфейси `DiscountStrategy`, `TaxCalculator`, `OrderRepository`; зрозумілі окремі реалізації.
- **Компроміс:** розділення на численні дрібні технічні компоненти збільшує кількість файлів, однак потрібно, щоб продемонструвати Protected Variations та Pure Fabrication.

### 4.3. YAGNI (додаткова перевірка)
- Не варто впроваджувати справжню SMTP-відправку, SQL БД або новий фреймворк **лише заради лабораторної**, якщо їх не вимагають критерії завдання. Натомість заглушки слід чітко називати і пояснювати.
- Не слід робити додатковий інтеграційний рефакторинг без з'ясування очікуваного формату здачі.

## 5. Перевірка метрик завдання 5 у межах Cross-Review

**Файл:** `Метрики1 (1).xlsx` (надана командою таблиця). Для класів, створених під час рефакторингу, прочерк у стовпцях «до» є **коректним**: класу не було в Legacy-версії. **Не** замінювати прочерки нулями.

**Пункти перевірки:**
1. Переконатися, що **CBO** рахується як число **різних проєктних типів**, з якими клас взаємодіє через поля, виклики, параметри, повернення, реалізацію інтерфейсів тощо; стандартні платформні типи не враховувати.
2. Заново перевірити рядок `OrderProcessor`: після рефакторингу він має явні взаємодії з `TaxCalculator`, `OrderRepository`, `NotificationService`, `ReceiptGenerator`, `Order` і типом, отриманим через `order.customer` (`Customer`); число `4` **не можна приймати без обґрунтованого підрахунку**.
3. Для `Order` пояснити прочерк у LCOM4 «до»: клас існував, але був анемічною структурою з полями та без бізнес-методів.
4. Для **LCOM4** побудувати граф публічних методів; ребра: спільне використання поля екземпляра або виклик одного методу іншим. Результати `1` у таблиці слід підтвердити цим розрахунком.
5. Додати інженерний висновок: що саме зменшило зв'язність / покращило згуртованість і які компроміси залишилися.
6. Для спільної фінальної архітектури не змішувати метрики різних реалізацій як єдиний показник.

**Поточний висновок:** таблиця метрик існує, але числові значення та межі підрахунку потребують верифікації; **усі нормативи не оголошуємо підтвердженими**, доки не завершено підрахунок.
