# ADR-001: Розподіл відповідальностей у системі обробки замовлень

## Статус

Proposed — архітектурне рішення запропоноване для реалізації у завданнях 2–4.

## Предметна область

Інтернет-магазин електроніки та побутової техніки.

Система обробляє замовлення клієнта: створює об'єкти, розраховує вартість товарів, знижку й ПДВ, формує текстовий рахунок та імітує збереження і надсилання email-повідомлення.

## 1. Контекст і аудит Legacy-коду

Початкова реалізація складається з п'яти класів: `Customer`, `Product`, `OrderItem`, `Order` та `LegacyOrderProcessor`.

Аналіз виявив такі проблеми.

### 1.1. Порушення інкапсуляції

У доменних класах поля мають модифікатор `public`.

Наприклад:

```java
public double price;
public int quantity;
public double finalAmount;
```

Будь-який зовнішній клас може встановити від'ємну ціну, некоректну кількість або довільну кінцеву суму. Доменні об'єкти самостійно не захищають свій стан.

### 1.2. Anemic Domain Model

`Order`, `OrderItem`, `Product` і `Customer` переважно зберігають дані.

Бізнес-логіка обчислення сум, знижок і податків знаходиться в `LegacyOrderProcessor`, хоча потрібні дані належать доменним сутностям.

Це суперечить GRASP Information Expert.

### 1.3. Bloated Controller

Єдиний метод `processConsoleOrder()` виконує одразу декілька незалежних обов'язків:

- Зчитування команд через `Scanner`.
- Створення клієнта, товарів і замовлення.
- Розрахунок суми товарів.
- Вибір знижки та розрахунок ПДВ.
- Зміну статусу замовлення.
- Формування й виведення текстового рахунку.
- Імітацію збереження та надсилання email.

Отже, консольний інтерфейс, бізнес-логіка та інфраструктурні операції змішані в одному методі.

### 1.4. Spaghetti Code та процедурний стиль

Метод містить довгий послідовний сценарій із залежностями між локальними змінними та прямими зверненнями до полів інших об'єктів.

Наприклад:

```java
subtotal += item.product.price * item.quantity;
```

Цей фрагмент порушує інкапсуляцію та посилює залежність обробника від внутрішньої структури `OrderItem` і `Product`.

Це процедурний код із надмірним знанням внутрішньої будови об'єктів, хоча складних переплетених переходів керування в ньому немає.

### 1.5. High Coupling

`LegacyOrderProcessor` безпосередньо використовує доменні класи `Customer`, `Product`, `OrderItem` та `Order`.

Також він залежить від деталей консольного введення через `Scanner` і сам відповідає за формування текстового представлення результату.

Зміни в структурі доменних об'єктів або способі введення даних можуть вимагати редагування цього класу.

### 1.6. Процедурні розгалуження

Правила знижок визначаються через `if / else if`:

```java
if ("VIP".equalsIgnoreCase(order.customer.type)) {
    discountRate = 0.15;
} else if ("Regular".equalsIgnoreCase(order.customer.type)) {
    discountRate = 0.05;
} else if ("New".equalsIgnoreCase(order.customer.type)) {
    discountRate = 0.0;
}
```

Додавання нового типу клієнта вимагатиме зміни цього блоку.

### 1.7. Додаткові технічні недоліки

- Грошові суми представлені типом `double`, що може створювати похибки округлення.
- Немає перевірки допустимості типу клієнта.
- Поле `totalSpent` задається, але не використовується для розрахунку знижки.
- Збереження замовлення та надсилання email лише імітуються повідомленнями в консолі.
- Відсутні автоматизовані тести бізнес-правил.

## 2. Архітектурне питання

**Яким об'єктам потрібно призначити відповідальність за обчислення вартості, створення замовлень та координацію процесу оформлення?**

## 3. Альтернативні рішення

**Варіант A — залишити всі операції в `LegacyOrderProcessor`.**

Перевага: мінімальна кількість класів і змін.

Недоліки: зберігаються порушення інкапсуляції, високе зачеплення та перевантажений контролер.

**Варіант B — перенести всі обчислення в окремий `OrderCalculator`.**

Перевага: клас обробника стане простішим.

Недоліки: калькулятор повинен знати внутрішню структуру `Order` і `OrderItem`; доменна модель залишиться переважно анемічною.

**Варіант C — розподілити відповідальності за GRASP.**

`OrderItem` обчислює суму конкретного рядка, `Order` керує своїми рядками та підсумковими розрахунками, а окремий Application Controller координує сценарій оформлення.

Створення рядків замовлення доручається `Order`, а технічні операції — окремим інфраструктурним компонентам.

Переваги: краща інкапсуляція, згуртованість і можливість незалежного тестування.

Недоліки: більше класів і необхідність чітко визначити контракти між ними.

## 4. Критерії оцінювання

**Information Expert:** відповідальність за обчислення належить об'єкту, який володіє необхідною інформацією.

**Creator:** `Order` створює або контролює створення `OrderItem`, оскільки містить відповідну колекцію.

**Controller:** координація оформлення відокремлена від консольного введення.

**Low Coupling:** класи повинні залежати від мінімально необхідної кількості інших компонентів.

**High Cohesion:** кожен клас повинен виконувати взаємопов'язані операції.

**Pure Fabrication:** технічні обов'язки збереження та повідомлень не повинні перевантажувати доменні сутності.

## 5. Прийняте архітектурне рішення

Обрано **варіант C**.

Запропоновано такий розподіл:

| Компонент | Відповідальність | GRASP |
|---|---|---|
| `OrderItem` | Розрахунок вартості товарного рядка | Information Expert |
| `Order` | Підсумкова сума, стан і додавання позицій | Information Expert, Creator |
| `Customer` | Зберігання й захист даних клієнта | Information Expert |
| `OrderController` | Координація оформлення | Controller |
| `ConsoleMenu` | Консольне введення та виведення | High Cohesion |
| `OrderRepository` | Абстракція збереження | Indirection, Pure Fabrication |
| `DiscountPolicy` | Контракт змінного алгоритму знижок | Polymorphism, Protected Variations |

Поліморфні реалізації знижок будуть додані під час виконання завдання 4.

## 6. Наслідки та інженерні компроміси

### Позитивні

- Доменні сутності отримають поведінку, пов'язану з їхніми даними.
- Зовнішній код не зможе довільно змінювати обчислені суми.
- Консольне введення буде відокремлено від бізнес-логіки.
- Збереження замовлень не залежатиме від способу консольної взаємодії.
- Бізнес-правила можна буде перевіряти незалежними тестами.

### Негативні

- Кількість файлів і класів збільшиться.
- Потрібно узгодити контракти між доменом, контролером і стратегіями знижок.
- Деякі доменні класи отримають додаткові залежності, тому необхідний контроль CBO.
- Рефакторинг потребуватиме перевірки збереження початкової бізнес-поведінки.

## 7. Перевірка результатів

Після рефакторингу планується:

- Порівняти бізнес-розрахунки до й після змін.
- Обчислити CBO для ключових класів із цільовим значенням не більше 4.
- Обчислити LCOM4 для рефакторених класів із цільовим значенням 1.
- Перевірити розподіл відповідальностей за дев'ятьма патернами GRASP.
- Провести командний Cross-Review.

Числові результати метрик буде наведено в завданні 5 після реалізації та фактичного вимірювання.

## Висновок

Початкова програма має анемічну доменну модель, порушення інкапсуляції, перевантажений консольний обробник та сильне зачеплення між обов'язками.

Обрано архітектурний рефакторинг за GRASP із перенесенням бізнес-логіки до відповідальних доменних сутностей, відокремленням контролера та інфраструктури.

Рішення обґрунтоване альтернативами, критеріями й компромісами та буде реалізоване в наступних завданнях.
